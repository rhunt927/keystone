# Project Brief: Accurate Topic-Learning App

## Origin / Problem Statement
Inspired by "Paladin: Learn History" — a mobile app that presents history as short animated stories with cartoon/AI-generated imagery and collectible characters. Investigation found real accuracy problems:
- Content appears to be generated by AI rather than written/verified by historians, despite marketing claims of being "fact-checked."
- Terms of service reportedly disclaim liability for factual accuracy.
- Specific example found: a Rosa Parks story blended documented history with dramatized/possibly invented framing.
- AI-generated images of real historical figures don't reliably resemble them.
- Format prioritizes narrative engagement (retention, subscription hooks) over accuracy.

**Goal:** build something in the same spirit — short, engaging, bite-sized learning content on topics of interest — but where every fact is traceable to a real source, not generated from model memory.

## Core Design Principle
Never let the model generate factual content purely from training data / memory. Every piece of content must be grounded in a real-time retrieval step, with the source shown to the user.

Pipeline:
1. User picks or is shown a topic/subtopic.
2. App performs a live web search (or hits curated/trusted APIs — see Open Questions) for that topic.
3. Model summarizes/writes short-form content *only* from what was retrieved — not from unaided memory.
4. Every fact, card, or story beat carries a visible source link/citation.
5. Content is cached once generated, so the same topic isn't re-searched/re-generated repeatedly (cost + consistency).

## Guardrails
- No AI-generated imagery depicting real, named historical/public figures as if photographic — use real (attributed) photos/art where possible, or clearly abstract/illustrative art otherwise.
- No fabricated dialogue or quotes attributed to real people unless sourced.
- Cite sources visibly in the UI, not buried in fine print.
- Prefer primary/reputable sources (encyclopedic, academic, major news/reference sites) over SEO content farms.

## Format / UX Ideas (carried over from Paladin's strengths, minus the accuracy problem)
- Short-form "lesson" cards, a few minutes each.
- Optional "deep dive" expansion per topic for more detail/context.
- Quizzes for retention.
- Possibly grouped into topic "paths" (e.g., a themed sequence of related figures/events).
- Source attribution attached to each card/lesson.

## Scope Question: Topics
Not yet decided whether this is history-only or broader (science, current events, etc.). Could start narrow (history) and generalize the pipeline later, since the search-and-cite mechanism isn't topic-specific.

## Tech Stack
To be based on the same free/low-cost tooling used in a previous app already built — bring that stack over into this project (framework, hosting, any APIs already in use). Key new requirement vs. that prior app: a search-grounding step (e.g., Claude API with web search tool enabled, or another search API) sitting between "user picks topic" and "content is generated."

## Open Questions to Resolve at Project Start
- History-only to start, or broader topics from day one?
- Where does search happen — client-side calls, or a lightweight backend?
- Which search/content source(s): general web search, Wikipedia API, a curated set of trusted reference sites, or a mix?
- How much caching/storage is needed (avoid re-searching same topics repeatedly)?
- Solo-use tool, or something intended to be shared/published later?
- iOS/Android/web — carry over the platform choice from the prior app unless there's a reason to change.

## Next Steps
1. Decide topic scope (or start history-only and generalize later).
2. Stand up the search-grounding step as a standalone piece first — prove out "topic in → sourced summary out" before building UI around it.
3. Reuse existing app's frontend/hosting patterns for the shell.
4. Design the card/lesson format with source attribution built in from the start, not bolted on.
